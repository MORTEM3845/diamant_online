# Архитектура Diamant Online

## Исполнение и хранение

Клиент — React и TypeScript, собираемые Vite в статические файлы. Cloudflare Worker обслуживает `/api/*`, а Static Assets — интерфейс и изображения. Оба работают с одного origin, поэтому отдельная настройка CORS или отдельный сервер приложения не нужны. Состояние хранится в Cloudflare D1, а не в памяти процесса Worker.

Клиент опрашивает комнату примерно раз в секунду. В фоновой вкладке интервал увеличивается до пяти секунд, после сетевых ошибок — до восьми. Приложение использует обычные HTTP-запросы, без WebSocket или Durable Objects. Такой обмен подходит пошаговой игре; его стоимость и пределы нагрузки следует измерять на выбранном аккаунте.

| Слой | Файлы | Ответственность |
| --- | --- | --- |
| Интерфейс | `src/client/main.tsx`, `styles.css` | Лобби, отображение партии, подтверждение действий, переподключение |
| Контракт | `src/shared/types.ts` | Игроки, карты, действия, внутреннее и публичное состояние |
| Движок | `src/shared/engine.ts` | Проверка действий, правила, случайная колода, боты, безопасная проекция |
| HTTP API | `src/server/worker.ts` | Проверка запроса, сессия, ограничения запросов, вызов движка |
| Хранилище | `src/server/repository.ts` | Чтение, атомарная запись по ревизии, срок жизни и очистка |
| Схема | `migrations/` | Таблицы комнат и ограничений запросов |

## Модель партии

`GameState` содержит полную серверную информацию: игроков, колоду, открытый путь, текущие секретные решения, исключённые карты, счётчики реликвий, итоги похода и журнал. Фазы: `lobby → decision → roundEnd → decision … → finished`.

В начале похода сервер перемешивает допустимые карты и сразу открывает первую. После безопасного открытия все исследователи в пещере подтверждают решения. Когда решения собраны, движок одновременно раскрывает их, обрабатывает возвращающихся и открывает следующую карту для оставшихся. Повтор опасности завершает поход сразу. После пятого похода вычисляются победители, включая несколько победителей при равенстве.

Функции движка возвращают новое состояние и не изменяют входной объект. Для проверяемых сценариев генератор случайности можно передать явно. В обычной работе используется `crypto.getRandomValues`; перемешивание Fisher–Yates выбирает индекс через rejection sampling, исключая смещение от остатка деления.

### Различия редакций

- `classic`: 30 карт; реликвий нет.
- `relics`: перед каждым походом добавляется новая реликвия из последовательности 5, 7, 8, 10, 12. Неоткрытые старые реликвии остаются в колоде.
- `legacy`: все пять реликвий замешаны в начале. До получения их `value` равен нулю; при получении назначается 5 или 10 по общему числу ранее спасённых реликвий. Ноль означает ещё не назначенную стоимость, а не нулевую награду.

Уничтоженные опасности, полученные реликвии и открытые потерянные реликвии не возвращаются при перемешивании. Путь сохраняется на экране итогов похода как история; он пересобирается при начале следующего.

Боты используют свою добычу и публичные сведения: открытые опасности, известные исключённые карты, остатки и реликвии на пути, количество неоткрытых карт. Они не читают порядок колоды или решения людей. После ухода последнего человека боты могут завершить текущий поход; следующая экспедиция автоматически не начинается.

## Сессии и видимость

Регистрация не нужна. При создании или присоединении сервер выдаёт отдельный случайный **256-битный bearer token**. Браузер хранит его в `localStorage` для конкретной комнаты. Сервер сохраняет SHA-256 токена вместе с идентификатором игрока, не сам токен. Токен не включается в пригласительную ссылку.

Токен подтверждает право управлять одним местом. Поэтому очистка данных браузера или переход на другое устройство не восстанавливают место автоматически. Несколько вкладок одного профиля разделяют токен. После выхода из лобби или исключения участника его серверная сессия отзывается.

В ответах используется исключительно `PublicRoom`, сформированный `publicRoom()`:

| Сведения | Доступность |
| --- | --- |
| Порядок неоткрытой колоды | Только сервер |
| Не раскрытые решения других игроков | Только сервер |
| Собственный подтверждённый выбор | Только соответствующий игрок |
| Кто уже подтвердил выбор | Все в комнате |
| Чужой банк и общий счёт | Скрыты до финала |
| Собственный банк и счёт | Видны владельцу |
| Открытая добыча, путь и приобретённые реликвии | Все в комнате |
| Хэши токенов и история request ID | Только сервер |

Гость со ссылкой получает публичное состояние без чужих закрытых сведений. В частности, знания кода комнаты недостаточно для подтверждения чужого решения. Закрытые сундуки — выбранное отображение настольного варианта; публичные события возвращения позволяют запоминать чужие приобретения, как за столом.

## Конкурентные действия и повторные запросы

В таблице комнаты хранятся сериализованное состояние и возрастающая `revision`. Изменение проходит так:

1. Прочитать текущую комнату и её ревизию.
2. Проверить токен игрока и `requestId`.
3. Применить действие к копии состояния, затем выполнить необходимые решения ботов.
4. Одной командой SQL записать новое состояние и увеличить ревизию **только если старая ревизия ещё совпадает**.
5. Если другой запрос успел записать состояние раньше, прочитать актуальную версию и повторить проверку.

Это compare-and-swap: одновременно отправленные решения не затирают друг друга, а последняя подтверждённая пара/группа решений открывает следующую карту один раз. В том же атомарном обновлении сохраняется идентификатор запроса. Для каждого участника хранятся последние 32 ID; повтор недавно обработанного запроса возвращает актуальное состояние без повторной мутации.

`choose` также содержит номер похода и хода. Устаревшее действие отклоняется. Подтверждённый выбор нельзя поменять до раскрытия; одинаковый повтор на том же ходу допустим. При исчерпании попыток записи API возвращает конфликт, а не перезаписывает более новое состояние.

Из-за отзыва собственной сессии повтор успешного `leave` после потери ответа может вернуть `401`. Он не возвращает игрока в комнату и не повторяет никаких игровых эффектов.

## API

Все изменяющие запросы передают JSON. Для действий игрока нужен заголовок `Authorization: Bearer …`.

| Метод | Путь | Назначение |
| --- | --- | --- |
| `GET` | `/api/health` | Проверка доступности API и таблицы D1 |
| `POST` | `/api/rooms` | Создание комнаты; `name`, `avatar`, `mode`, опционально `practice` |
| `GET` | `/api/rooms/:code` | Снимок комнаты с видимостью для указанной сессии или гостя |
| `POST` | `/api/rooms/:code/join` | Присоединение в лобби; `name`, `avatar` |
| `POST` | `/api/rooms/:code/action` | Действие `{ requestId, action }` |

Сервер проверяет типы, длины, доступность действия в текущей фазе и полномочия участника. JSON ограничен по размеру. Для записывающих маршрутов проверяется origin; запросы с другого сайта отклоняются. Ограничители создания комнат, входа и действий считаются в D1 по хэшу IP и временному окну. Отключение лимитов предназначено для локальных интеграционных тестов.

## Полномочия и переподключение

Организатор меняет редакцию, добавляет ботов, удаляет игроков в лобби, запускает партию и реванш. Для старта нужны 3–8 участников и готовность всех людей. Изменение редакции сбрасывает готовность. После выхода организатора из лобби его роль переходит следующему человеку.

Начать следующий поход может любой человек за столом. Это управление паузой между раундами, не изменение игрового результата. Во время похода нельзя исключать игроков, чтобы использовать удаление как преимущество при делении сокровищ.

Соединение не является членством в комнате. При закрытии вкладки место, добыча и подтверждённое решение сохраняются. После обновления страницы клиент получает актуальную ревизию. Автоматического таймера, отступления или замены человека ботом нет: без решения отключившегося участника активный поход ждёт его возвращения.

## Срок жизни, миграции и публикация

Каждая успешная запись продлевает срок жизни комнаты. По умолчанию `ROOM_TTL_HOURS=168`, то есть семь дней. Чтение не продлевает срок. Плановый обработчик удаляет истёкшие комнаты и устаревшие счётчики ограничений запросов. Локальная и удалённая D1 — разные базы.

`npm run dev` последовательно собирает проект, применяет локальные миграции и запускает Wrangler на порту 5173. `npm run deploy:setup` готовит привязку выделенной D1 через авторизованный Wrangler. `npm run deploy` выполняет проверки, применяет удалённые миграции и публикует Worker. GitHub Actions использует собственный API-токен и ID аккаунта/базы из настроек репозитория. Подробные команды приведены в [README](../README.md).

Неоткрытые карты и секреты не должны попадать в диагностические HTTP-ответы или клиентские логи. При изменении схемы внутреннего состояния необходимо учитывать `schemaVersion` и уже сохранённые комнаты; миграция таблиц сама по себе не преобразует JSON существующих партий.

## Проверки и границы

Тесты движка покрывают пограничные правила, приватность проекций и полные партии по всем редакциям. Интеграционные тесты запускают Worker с D1 в Miniflare, проверяя API и конкурентные записи. `npm run check` объединяет типизацию, тесты и сборку.

Отдельные дополнения, пользовательские аккаунты, межустройственная передача места, рейтинг и автоматическая модерация отключений не реализованы. Производственная нагрузка, квоты конкретного Cloudflare-аккаунта и длительные многопользовательские сессии требуют отдельной проверки после публикации. Издательские PDF используются только для исследования и не публикуются; приложение использует собственные изображения из `public/art/`.
